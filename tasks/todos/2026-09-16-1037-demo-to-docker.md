# 把 demo.jant.me 换成 Docker 版

## 目标

用 Docker + Node 版 demo **直接取代** demo.jant.me 现在的 Workers 版，内容相同，每晚自动重置。

- **不做并行测试站**。直接用 `demo.jant.me`，出了问题回滚到 Workers 版。
- **切 DNS 之前，Workers 版完全不动；切换之后也保留它作为回滚**，不要删任何 Workers demo 的资源。
- **没有性能目标**。文章页的串行查询已在另一个会话里解决，Workers 版不一定更慢，
  单机版对离机器远的读者反而可能更慢。本任务的理由是让 Docker 部署路线有一个
  真实的生产实例。不要拿「变快了」当验收标准。

## 定位：它是 `@jant/core` 的一个部署，与 hosted 同类

Docker demo **不是**「把 `sites/demo` 搬到 Docker」。它的每个组成部分都不在 `sites/demo` 里：

| 组成 | 在哪 |
|---|---|
| 部署配置 | studio `external-apps/jant-demo/` |
| 内容 | `sites/demo-source/canonical/snapshot/` |
| 运行时 | 由 `packages/core` 构建的镜像，与 hosted 同一个 Dockerfile |
| 新增能力 | `packages/core`（无界面初始化 CLI 命令） |
| `DEMO_EMAIL` 等值 | 抄一次进 studio 的 env，之后无关联 |

所以 **jant 仓库里只改 `packages/core` 和 `.github/workflows/`，不新建任何 demo 专用的站点目录，
不碰 `sites/demo`。**

`sites/demo` 现在一个目录身兼两职 —— create-jant 的 starter 模板源，和线上 Workers demo 的部署
（`scripts/bootstrap-demo.mjs`、`docs/internal/`、`wrangler.toml` 里标了 `@create-jant: @remove`
的 demo 配置）。这是本任务一直显得乱的根源，留给「Workers demo 下线」那个后续任务处理，见文末。

## 已定的设计

| 项 | 决定 |
|---|---|
| 域名 | 一开始就是 `demo.jant.me` |
| 代码版本 | **跟 main**，部署 main 上最近一次 CI 通过的 SHA，与 hosted 一致 |
| 数据库 | SQLite，**不挂卷**，容器每次启动都从快照重建 |
| site id | **固定为快照 `meta.json` 里的 id**，重建时读取，不写死 |
| 媒体 | R2 via S3 driver，**单独建一个桶** |
| 静态资源 | 仿照 hosted 的 `jant assets upload` + `ASSET_BASE_URL`，放在同一个桶的 `_assets/` 下 |
| 快照送达 | 构建时从同一份源码检出复制进 `deploy-dist/`，随部署同步到服务器，只读挂载 |
| 每晚重置 | jant 仓库的 GitHub 定时任务，**重新部署**一次 |
| 失败发现 | 定时任务从外部确认已重置，确认不了就开 issue |
| 部署配置位置 | `/Users/green/project/studio/external-apps/jant-demo/`，仿照 `external-apps/jant/` |

## 关键设计的理由

### 为什么删库重建，而不是 `--replace`

`--replace` 是为「把内容快照恢复进一个真实站点」设计的，它保留站长的其他设置。demo 要的是
「把游乐场恢复原状」，拿前者当后者用会漂移 —— Workers 版上已经发生：控制台语言 2026-08-04
被改成中文后，43 次重置都没恢复；新手提示 2026-05-14 被点掉后，此后的访客都看不到。
demo 模式只锁 `NOINDEX` 一个设置，`--replace` 只恢复 `SNAPSHOT_SETTING_KEYS` 里的 19 个。

删库重建不依赖任何「该清什么」的手写清单，新表和新设置天然被清掉；新库里没有 API token 和
上传会话，省掉两个清理步骤。代价是测不到「旧库 + 新迁移」的升级路径（`migration-rehearsal.yml`
部分覆盖）。

### 为什么 SQLite 不挂卷、容器启动即重建

既然每晚都删库，数据库本来就没有理由持久化。不挂卷解决了 studio 发布方式带来的两个问题：

- **studio 用 `docker rollout` 零停机发布**：先起新容器、等健康、再删旧容器，发布期间新旧容器
  同时运行。挂同一个 SQLite 卷时，`pre-deploy` 的 `jant migrate` 会在旧容器服务时改表，启动时
  重建会删掉旧容器还开着的文件。不挂卷则每个容器用自己私有的库，互不影响。
- **不需要「停应用」**：重启或重新部署容器就等于重建。

hosted 用 Postgres，数据库在容器外，所以 studio 的发布流程没遇到过这些问题。

发布期间新容器清桶时旧容器仍在服务，媒体会 404 几秒。demo 可以接受。

### 为什么固定 site id

媒体 URL 里带 site id：`https://<媒体域名>/media/{siteId}/files/med_xxx.png`。每晚变的话，
分享出去的 og:image 预览、feed 阅读器里的图片一天后失效，CDN 缓存每天作废。

固定后，快照里的文件名本身稳定，重建后对象 key 每晚完全一样。这也补全了快照本来的设计：
`jant site snapshot export` 的说明是 "preserves IDs, storage keys, and object files"，只有
site id 原本是随机生成再 remap 的。

用快照自己的 id（当前 `sit_01kn8jq3t4famtyg9hjd074ckr`）：导入时不需要 remap，省掉
`rewriteSnapshotSiteIdentifiers` 对整份 SQL 的全局替换，`validateSnapshotTargetSite` 会校验两者
一致；重建时从 `meta.json` 读，demo-source 若换了 id 会自动跟上。与 demo-source 同 id 不冲突 ——
不同的库、不同的桶。

### 为什么单独建桶

每晚清桶是批量删除。共用桶时前缀取错就会删到别的数据；单独建桶后清桶完全不依赖 site id。

媒体域名以后换只是改配置：已核实 canonical 快照里没有任何绝对 URL，文章 HTML 里也没有 `<img>`，
媒体 URL 在渲染时由 `S3_PUBLIC_URL` + key 拼出来。

### 为什么跟 main，以及快照为什么必须与镜像同一个 commit

这个项目实际上把 main 当生产：hosted 从 main 构建（`vite.shared.ts` 注释："hosted builds that
ship unreleased commits"），demo-source 用 `workspace:*` 跑 main，`snapshot-canonical-replay.test.ts`
守的是「已提交快照能导入 **main 的 head schema**」。

**硬规则：快照与镜像取自同一个 commit。** 跟版本号却读 main 的快照，main 加了动快照表的迁移后
导入会报 `no column named X`；镜像是上周的 main、快照另外拉今天的 main，同样错位。只要同 commit
成立，demo 部署得晚一点也安全，只是展示得旧一点。

### 为什么快照通过 `deploy-dist` 送达

studio 的 `compose-build` 把 `jant-me/jant` 检出到临时目录，用检出根目录的 `Dockerfile` 构建镜像，
渲染后的 compose、`.env`、`version.txt` 写进 `deploy-dist/`；ansible 再用 `synchronize`
（`delete: yes`）把 `deploy-dist/` 整个同步到服务器。

同一次构建里快照就在那份检出中，所以从检出复制进 `deploy-dist/snapshot/`，同 commit 是**结构上**
保证的，不用记 SHA、不用运行时联网。

没选的做法：打进通用镜像（hosted 和所有自部署用户都会带上 demo 内容）；给 demo 单独写
Dockerfile（studio 固定用源码根目录的 `Dockerfile`，spec 不鼓励）；重建时按 SHA 去 GitHub 拉
（运行时拿不到 SHA，GitHub 不能按目录下载）；`build.sh` 自定义模式（绕开整个标准流程）。

### 为什么每晚由 GitHub 定时重新部署

- **studio 的 `-cron` sidecar 做不到**：重启主容器要挂 `docker.sock`（等于宿主机 root，studio 里
  没有任何服务这么做）；数据库在主容器私有文件系统里，sidecar 也碰不到。
- **容器到点自己退出再由重启策略拉起**：重建失败时新进程起不来、反复重启，demo 直接挂；代码也会
  停在上次部署的版本。
- **定时重新部署**：rollout 零停机；失败时回滚到旧容器；顺带每晚跟上 main。已核实 studio 的版本号
  是时间戳（`get_version` 返回 `date -u +%Y%m%d%H%M%S`），每次部署都是新 tag，rollout 一定起新容器。

放在 **jant 仓库**：`ci.yml` 的 `deploy-studio-prod` 已经在 CI 通过后调用 `deploy-studio.yml` 部署
hosted，jant 仓库本来就持有 `BUILD_REPO_TOKEN`。推送 main 不会顺带部署 jant-demo ——
`deploy-studio.yml` 里服务名写死为 `jant`。

**部署 main 上最近一次 CI 通过的 SHA，不是 main 最新提交**：hosted 有 CI 关卡，定时任务没有；
用 CI 通过的 SHA，demo 跑的正好是 hosted 在跑的 commit。

### 为什么重建先清桶，以及为什么必须外部验证

曾考虑「先上传、再清理」，让重建失败时 rollout 回滚后的旧容器媒体完好。**不采用**：

- 这条链路里**没有任何失败通知**：`deploy-studio.yml` 发出 dispatch、打印 "Triggered" 就结束，
  不等结果，jant 这边的定时任务永远显示成功；build 仓库也没有失败通知。
- 没有通知时，「回滚后一切正常」等于把失败藏起来 —— demo 悄悄不再重置、不再跟 main，可能拖几周。
  看得见的故障比看不见的好。
- 先清桶更简单：只需「保留 `_assets/`，其余全删」，不用知道快照里有哪些 key。

真正要补的是通知：**定时任务 dispatch 之后等一段时间，从外部请求 demo.jant.me 确认新版本已上线，
确认不了就用 `report-failure.yml` 开 issue。** 这不依赖 build 仓库的实现，构建、部署、rollout
回滚、重建失败任何一环都能抓到。

具体检查什么由实现者设计。已核实现在公开 HTML 里没有版本号（资源路径用内容 hash），无法从外部判断
「是不是今晚新起的容器」。候选：让 `/readyz` 返回构建 SHA，定时任务比对自己发出的 SHA。
`CORE_VERSION` 已经是 `${version}-${buildId 前 16 位}`（`lib/version.ts`、`vite.shared.ts`）。

## 硬约束（漏掉任何一条都会白干）

1. **清桶必须有两道护栏。** 风险是清桶因配置错误指向 Workers demo 的 `jant-demo-media` 或 hosted 的
   `jant-cloud-media`。
   - **R2 token 权限只限这一个桶**，配错时请求被拒绝而不是删东西。主护栏。
   - **重建代码断言 `S3_BUCKET` 等于专用桶名**，不等就拒绝运行。兜底。
2. **清桶保留 `_assets/`，删掉其余所有对象。** 枚举要删的前缀，新增前缀时会静默泄漏；枚举要留的，
   出错时静态资源丢失、页面立刻坏掉。选响亮的失败方式。
3. **site id 固定为快照 `meta.json` 的 id，重建时读取。** 验证：重建后 site id 等于 `meta.json` 的 id，
   导入没有触发 remap。
4. **快照必须与镜像同一个 commit**，从同一次构建的源码检出里取，不要在运行时另外拉。
5. **不挂卷必须显式做到。** `Dockerfile` 有 `VOLUME ["/var/lib/jant"]` 且 `ENV DATA_DIR=/var/lib/jant`：
   compose 里不挂载时 Docker 会自动建**匿名卷**，每次发布留下一个，磁盘持续泄漏。用 `tmpfs` 挂到
   数据目录，或把 `DATA_DIR` 指到非 `VOLUME` 路径。
6. **新桶暂时不要用 `demo-media.jant.me`。** 它绑在 Workers demo 的桶上，回滚要用。
7. **SQLite，不用 Postgres。** 快照是 `"dialect": "sqlite"`，`assertSnapshotDialectMatches` 拒绝跨方言。
8. **独立的 Jant 实例，单站点。** `DEMO_MODE` 是 `envOnly: true`，实例级。
9. **仿照 hosted 但不要照抄：**
   - `compose.deploy.yaml` 的 `environment` 写死了 `SITE_RESOLUTION_MODE: host-based` —— 这里单站点
   - `.env.tpl` 的 `DATABASE_URL` 指向 Postgres —— 这里用 SQLite
   - `volumes:` 挂了数据卷 —— 这里不挂（约束 5）
   - `pre-deploy` 里的 `-migrate` —— 这里不需要，容器启动时自己迁移
   - R2 凭据 `COMMON_CLOUDFLARE_S3_*` —— 不要用，用只限专用桶的 token（约束 1）。另外那组 secret 名
     `COMMON_CLOUDFLARES3_SECRET_ACCESS_KEY` 少一个下划线，对照模板时别被绊到
10. **studio 只在 `__PROJECT` 为 `jant` 时传 `JANT_BUILD_ID`**（`scripts/build-external-app.sh`）。
    jant-demo 也需要，否则镜像里 `CORE_VERSION` 不含 SHA，外部验证无从比对。
11. **域名只出现在环境变量里**，不要写进代码、脚本名、任务名、文件名。
12. **不要往 `sites/demo/` 加文件**，也不要新建 demo 专用的站点目录。`sites/demo` 是 create-jant 模板源：
    `packages/create-jant/package.json` 的 `copy-template` 用 `rsync -a ../../sites/demo/ template/`
    整目录拷贝。
13. **demo-source 留在 Cloudflare 不动。**

## 容器启动时的重建流程

```
断言 S3_BUCKET 是专用桶
清桶：保留 _assets/，删除其余所有对象
jant migrate（容器私有的空库）
读快照 meta.json 的 site id → 无界面初始化：建该 id 的站点 + demo 账户
jant site snapshot import --replace --node --path <挂载的快照>
jant start
```

`pre-deploy` 里保留 `jant assets upload`（它不依赖数据库）。健康检查的 `start_period` 可能要调大。

「清桶只留 `_assets/`」这类危险操作只有 demo 需要，**不要做成所有用户都能调用的 `jant` 命令**，
放在部署侧。

## 上线与回滚

### 切 DNS 时必须同时停掉 Workers 的每晚重置

`scripts/demo-public/` 下的 `clear-api-tokens.mjs`、`verify.mjs`、`import-canonical.mjs`、
`clear-content.mjs` 都用 `resolveDemoPublicSiteUrl()` 取目标 URL，回退到 `sites/demo/wrangler.toml`
的 `SITE_ORIGIN = "https://demo.jant.me"`。DNS 切走后 `reset-demo.yml` 会打到新容器上：拿 Workers
的 `INTERNAL_ADMIN_TOKEN` 调新站的内部接口、拿新站页面对照 Workers 的 D1，每晚失败并开 issue。

### 上线步骤（Owen 手动）

1. 部署容器
2. **切 DNS 前先冒烟验证**：在服务器上直接对容器发请求（带 `Host: demo.jant.me`），确认首页、文章页、
   媒体、静态资源、`DEMO_EMAIL` / `DEMO_PASSWORD` 登录都正常
3. 在 Cloudflare 把 `demo.jant.me` 从 Worker 上解绑，改指向容器源站（代理模式）
4. **停掉 `reset-demo.yml` 的定时触发**，启用新的每晚定时任务
5. Worker、D1 `jant-demo-db`、R2 `jant-demo-media`、`demo-media.jant.me` **全部保留**，这就是回滚

### 回滚

1. 把 `demo.jant.me` 重新绑回 Worker
2. 停掉新的每晚定时任务，恢复 `reset-demo.yml` 的定时触发并手动跑一次
