# 把 demo.jant.me 换成 Docker 版

## 目标

用 Docker + Node 版 demo **直接取代** demo.jant.me 现在的 Workers 版，内容相同，每日自动重建。

- **不做并行测试站**。直接用 `demo.jant.me`，出了问题回滚到 Workers 版。
- **切 DNS 之前，Workers 版完全不动；切换之后也保留它作为回滚**，不要删任何 Workers demo 的资源。
- **没有性能目标**。文章页的串行查询已在另一个会话里解决，Workers 版不一定更慢，
  单机版对离机器远的读者反而可能更慢。本任务的理由是让 Docker 部署路线有一个
  真实的生产实例。不要拿「变快了」当验收标准。

## 已定的设计

| 项 | 决定 |
|---|---|
| 域名 | 一开始就是 `demo.jant.me` |
| 数据库 | SQLite |
| 每日重建 | **删库重建**：清掉本站对象 → 删 SQLite → 从空库迁移 → 建站和 demo 账户 → 导入快照 |
| site id | **固定为快照 `meta.json` 里的 site id**，重建时读取，不写死 |
| 媒体 | R2 via S3 driver，**单独建一个桶** |
| 静态资源 | 仿照 hosted 的 `jant assets upload` + `ASSET_BASE_URL`，放在同一个桶的 `_assets/` 下 |
| 部署配置位置 | `/Users/green/project/studio/external-apps/jant-demo/`，仿照 `external-apps/jant/` |

### 为什么删库重建，而不是 `--replace`

`--replace` 是为「把内容快照恢复进一个真实站点」设计的，它保留站长的其他设置。
demo 要的是「把游乐场恢复原状」，拿前者当后者用会漂移 —— Workers 版上已经发生了：
控制台语言 2026-08-04 被改成中文后，43 次重置都没恢复；新手提示 2026-05-14 被点掉后，
之后的访客都看不到。demo 模式只锁 `NOINDEX` 一个设置，`--replace` 只恢复
`SNAPSHOT_SETTING_KEYS` 里的 19 个。

删库重建：每天早上真正干净；**不依赖任何「该清什么」的手写清单**；存储清得更彻底；
新库里没有 API token 和上传会话，省掉两个清理步骤。
代价：测不到「旧库 + 新迁移」的升级路径（`migration-rehearsal.yml` 部分覆盖）；
重建期间短暂停服、访客全部登出；建站逻辑每晚从零跑，必须可靠。

### 为什么固定 site id

媒体 URL 里带 site id：`https://<媒体域名>/media/{siteId}/files/med_xxx.png`。

site id 每晚变，所有媒体 URL 就每晚变：分享出去的 og:image 预览一天后失效，feed 阅读器里的
图片一天后失效，CDN 和图片变换缓存每天作废。长期对外的 demo 不该这样。

固定之后，快照里的媒体文件名本身稳定，重建后对象 key 每晚完全一样，昨天的 URL 重建完又能用。
这也补全了快照本来的设计：`jant site snapshot export` 的说明是
"preserves IDs, storage keys, and object files"，文章 id、媒体 id、存储 key 都刻意保留，
**只有 site id 原本是随机生成再 remap 的**。

**用快照自己的 site id**（当前是 `sit_01kn8jq3t4famtyg9hjd074ckr`），因为：

- 建站 id 等于快照 id，导入时**不需要 remap**，省掉 `rewriteSnapshotSiteIdentifiers` 对整份 SQL
  做的全局字符串替换；`validateSnapshotTargetSite` 会校验两者一致
- 不用新增配置项
- 重建时从 `meta.json` 读，不写死：demo-source 若被重建换了 id，下一次重建自动跟上
  （媒体 URL 随之变一次，罕见）
- 与 demo-source 同 id 不冲突：不同的库、不同的桶

**需要改的代码**：站点 id 现在由 `src/services/site.ts` 的 `resolveSingleSite` 在插入时用
`createEntityId("site")` 随机生成，`EnsureSingleSiteOptions` 只有 `{ host, key, pathPrefix }`。
给它加一个可选的 `id`，建站时使用。

### 为什么单独建桶

删库重建要先清掉本站在 R2 上的对象，这是批量删除。共用桶时一旦前缀取错，就会删到别的数据。
单独建桶后清桶**完全不依赖 site id**：整桶只保留 `_assets/`，其余全删。

### 媒体域名以后可以随便换

已核实：canonical 快照里**没有任何绝对 URL**，文章 HTML 里也没有 `<img>`。媒体通过 `media`
表的存储 key 引用，URL 在渲染时由 `S3_PUBLIC_URL` + key 拼出来。所以换媒体域名只是改配置。

## 硬约束（漏掉任何一条都会白干）

1. **清桶必须有两道护栏。** 风险是清桶操作因配置错误指向 Workers demo 的 `jant-demo-media`
   或 hosted 的 `jant-cloud-media`。
   - **R2 token 权限只限这一个桶。** 配错时请求直接被拒绝，而不是删东西。这是主护栏。
   - **重建代码里断言 `S3_BUCKET` 等于专用桶的名字**，不等就拒绝运行。兜底。
2. **清桶时保留 `_assets/`，删掉其余所有对象。** 不要只删 `media/` 和 `trash/`：
   枚举要删的前缀，新增前缀时会静默泄漏；枚举要留的前缀，出错时静态资源丢失，
   页面立刻坏掉，验证会抓到。选响亮的失败方式。
3. **site id 固定为快照 `meta.json` 的 id，重建时读取。** 验证里检查：重建后的 site id 等于
   `meta.json` 的 id，且导入过程没有触发 remap。
4. **新桶暂时不要用 `demo-media.jant.me`。** 它绑在 Workers demo 的桶上，回滚要用。
   新桶先用另一个公开域名；Workers demo 下线后再改绑（只改配置，见上文）。
5. **SQLite，不用 Postgres。** 同机 hosted 在跑 PG，不要复用。canonical 快照是
   `"dialect": "sqlite"`，`assertSnapshotDialectMatches` 拒绝跨方言导入。
6. **独立的 Jant 实例，单站点。** `DEMO_MODE` 是 `envOnly: true`，实例级。
7. **仿照 hosted 但不要照抄这三处：**
   - `compose.deploy.yaml` 的 `environment` 里写死了 `SITE_RESOLUTION_MODE: host-based`
     —— 这里必须是单站点
   - `.env.tpl` 的 `DATABASE_URL` 指向 Postgres —— 这里用 `DATA_DIR` + SQLite
   - hosted 的 R2 凭据 `COMMON_CLOUDFLARE_S3_*` —— **不要用**，用只限专用桶的 token（约束 1）。
     另外那组 secret 名 `COMMON_CLOUDFLARES3_SECRET_ACCESS_KEY` 少一个下划线，
     对照 hosted 模板时别被绊到
8. **重建期间应用必须停着。** 删 SQLite 文件（含 `-wal`、`-shm`）时不能有进程开着它。
9. **域名只出现在环境变量里**，不要写进代码、脚本名、任务名、文件名。
10. **不要往 `sites/demo/` 加文件。** 它是 create-jant 模板源：
    `packages/create-jant/package.json` 的 `copy-template`（`prepublishOnly` 触发）用
    `rsync -a ../../sites/demo/ template/` 整目录拷贝。
11. **demo-source 留在 Cloudflare 不动。**

## 上线与回滚

### 切 DNS 时必须同时停掉 Workers 的每晚重置

`scripts/demo-public/` 下的 `clear-api-tokens.mjs`、`verify.mjs`、`import-canonical.mjs`、
`clear-content.mjs` 都用 `resolveDemoPublicSiteUrl()` 取目标 URL，它回退到
`sites/demo/wrangler.toml` 的 `SITE_ORIGIN = "https://demo.jant.me"`。

DNS 切到容器之后，`reset-demo.yml` 仍会每晚运行并**打到新的容器上**：
`clear-api-tokens` 拿 Workers 的 `INTERNAL_ADMIN_TOKEN` 去调新站的内部管理接口，
`verify` 拿新站的页面去对照 Workers 的 D1。结果是每晚失败，并经 `report-failure.yml`
每晚开一个 issue。

### 上线步骤（Owen 手动）

1. 部署容器，触发一次重建
2. **切 DNS 之前先冒烟验证**：在服务器上直接对容器发请求（带 `Host: demo.jant.me`），确认首页、
   文章页、媒体、静态资源、`DEMO_EMAIL` / `DEMO_PASSWORD` 登录都正常
3. 在 Cloudflare 把 `demo.jant.me` 从 Worker 上解绑，改指向容器源站（代理模式）
4. **停掉 `reset-demo.yml` 的定时触发**
5. Worker、D1 `jant-demo-db`、R2 `jant-demo-media`、`demo-media.jant.me` **全部保留**，这就是回滚

### 回滚

1. 把 `demo.jant.me` 重新绑回 Worker
2. 恢复 `reset-demo.yml` 的定时触发，并手动跑一次（停跑期间可能积了访客改动）

### 稳定之后（独立的后续任务，不在本任务范围）

- 下线 Workers demo：Worker、D1、`reset-demo.yml`、`deploy-demo.yml`、`scripts/demo-public/`、
  `demo-*` mise 任务、`sites/demo/scripts/bootstrap-demo.mjs`、`sites/demo/wrangler.toml` 里
  标了 `@create-jant: @remove` 的 demo 专用配置。**`sites/demo/` 本身必须保留**（模板源），
  demo-source 的导出链也保留
- 把 `demo-media.jant.me` 改绑到新桶（只改配置），删掉 `jant-demo-media` 桶
- Workers 版的设置漂移随它一起消失，不用单独修

## 可以复用的

### 直接复用

| 东西 | 位置 |
|---|---|
| canonical 快照 | `sites/demo-source/canonical/snapshot/` |
| Docker 镜像 | hosted 用的同一个构建（`__REPO=jant-me/jant`） |
| 部署结构 | studio `external-apps/jant/`：`.env.tpl` 契约、`compose.deploy.yaml`、`pre-deploy` profile 跑 migrate 与 assets upload、`/readyz` healthcheck、`shared` 网络 |
| 容器内 CLI | `jant migrate`、`jant site snapshot import --replace --node`（导入命令强制要求 `--replace`，空库上它等于直接导入） |
| 前缀列举 | S3 driver 实现了 `listAllKeys(prefix)`（`src/lib/storage.ts`），清桶可以用 |
| 失败上报 | `.github/workflows/report-failure.yml` |
| 快照可加载性 | `src/__tests__/snapshot-canonical-replay.test.ts` 已证明快照能导进迁移到 head 的 SQLite |

### 复用逻辑，但要抽出来

`packages/core/dev/scripts/reset-node-dev.ts`（`mise run db-node-rebuild-demo`）的流程和
删库重建几乎一样：

```
resetLocalFilesystem     删 SQLite（含 -wal/-shm）和本地媒体目录
migrate                  迁移到 head
ensureLocalDevShell      建站（第 392 行 siteService.ensureSingleSite()）、建管理员账户、完成 onboarding、种默认导航
importCanonicalSnapshot  导入快照
```

但它是 dev 取向的：写 `packages/core/.env.node`、用 dev 密码、配 `DEV_API_TOKEN`、
**只支持本地存储**。**不要复制一份改改**，把建站、建账户和删库的逻辑抽出来让 dev 脚本和
Docker demo 共用，dev 脚本行为不变。清 R2 是新增的一步；导入快照走 CLI，
它通过 `createStorageDriver` 支持 S3。

**唯一真正缺的生产能力是「在 Node 上建一个指定 id 的站点和一个已知密码的 demo 账户」**，
目前没有任何生产 CLI 命令能做。

### 不能复用

| 东西 | 原因 |
|---|---|
| `scripts/demo-public/clear-storage.mjs` / `clear-content.mjs` / `verify.mjs` | 绑死 `queryRemoteD1` |
| `scripts/demo-public/clear-api-tokens.mjs` | 删库重建用不着 —— 新库里没有 token |
| `sites/demo/scripts/bootstrap-demo.mjs` 与 `ensureManagedSetup` | `flag` 直接传给 wrangler（`dev-auth-db.mjs` 的 `runWrangler([flag, ...])`），只认 `--local` / `--remote` |

## 每日重建

```
停应用
断言 S3_BUCKET 是专用桶
清桶：保留 _assets/，删除其余所有对象
删 SQLite（含 -wal、-shm）
jant migrate
读快照 meta.json 的 site id，用它建站；建 demo 账户（DEMO_EMAIL / DEMO_PASSWORD）
jant site snapshot import --replace --node --path <快照>
起应用
验证（含：site id 等于 meta.json 的 id、没有触发 remap、静态资源能加载）
```

## 背景（为什么不是为了性能）

最初以为 demo 慢是「跨太平洋 D1 往返」。实测证伪：`/readyz` 减 `/healthz` ≈ 34ms，
是同区副本，read replication 生效。真正原因是文章页约 13 次串行查询，已在另一个
会话里解决。也因此**不要试 smart placement**，它会把 Worker 从副本旁边挪走。
