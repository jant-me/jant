# 用 demo-node.jant.me 验证 Docker 版 demo

## 目标

在 `demo-node.jant.me` 起一个**与现有 demo 并行**的 Docker + Node 版 demo，
内容与 demo.jant.me 相同，每日自动重建。

- **现有 demo.jant.me 完全不动**。它继续跑在 Workers 上，每晚照常重置。
- 切不切换是之后的独立决定，不在本任务范围。
- **没有性能目标**。文章页的串行查询已在另一个会话里解决，Workers 版不一定更慢，
  单机版对离机器远的读者反而可能更慢。本任务的理由是让 Docker 部署路线有一个
  真实的生产实例。不要拿「变快了」当验收标准。

## 部署形态

仿照 hosted 的部署：`/Users/green/project/studio/external-apps/jant/`。
demo-node 的部署配置放 `/Users/green/project/studio/external-apps/jant-demo/`。

- **数据库**：SQLite，持久化卷，**不每晚删除**（理由见「每日重建」）
- **媒体**：R2 via S3 driver，**复用 demo.jant.me 的桶** `jant-demo-media`，
  公开域名 `demo-media.jant.me`，图片变换 `demo-media.jant.me/cdn-cgi/image`
- **静态资源**：仿照 hosted 的 `jant assets upload` + `ASSET_BASE_URL`
- **demo 配置**：`DEMO_MODE` / `DEMO_EMAIL` / `DEMO_PASSWORD`，值见 `sites/demo/wrangler.toml`

## 为什么可以共用 demo.jant.me 的 R2 桶

本文件早先版本说「共用会互相删对象」，**那是错的**。

- 所有对象 key 带 site id：`media/{siteId}/files/…`、`media/{siteId}/assets/…`、
  `trash/{siteId}/…`（`src/lib/upload.ts`、`src/services/media.ts`）
- 所有清理路径由站点自己的 DB 驱动。`bin/commands/site/snapshot/import.js` 里：
  `currentKeys = buildSnapshotStorageQuery(targetSite.id)`，
  `keysToDelete = currentKeys - snapshotKeys`
- demo-node 建站会拿到新的 site id，与 demo.jant.me 的 `sit_01km9gzpdweh68kr42nhjvfxjz`
  前缀不重叠

共用反而更贴近目标：hosted 本身就是 Node + R2，Docker 部署文档推荐的生产组合也是
SQLite + S3；本地存储 dogfood 的是更不生产的组合。

## 硬约束（漏掉任何一条都会白干）

1. **SQLite，不用 Postgres。** 同机 hosted 在跑 PG，不要复用。canonical 快照是
   `"dialect": "sqlite"`，`assertSnapshotDialectMatches` 拒绝跨方言导入。
2. **独立的 Jant 实例，单站点。** `DEMO_MODE` 是 `envOnly: true`，实例级。
3. **不要照抄 hosted 的三处**：
   - `compose.deploy.yaml` 的 `environment` 里写死了 `SITE_RESOLUTION_MODE: host-based`
     —— demo-node 必须是单站点
   - `.env.tpl` 的 `DATABASE_URL` 指向 Postgres —— demo-node 用 `DATA_DIR` + SQLite
   - hosted 模板的 secret 名是 `COMMON_CLOUDFLARES3_SECRET_ACCESS_KEY`（CLOUDFLARE 与 S3
     之间**少一个下划线**），ID 是 `COMMON_CLOUDFLARE_S3_ACCESS_KEY_ID`。引用时名字要
     与 studio 的 secret 存储一致，**不要顺手「修正」**
4. **SQLite 不能每晚删。** 用 R2 时清理由 DB 驱动：删库后新库不知道昨天的对象，它们
   永远没人删；若 site id 随重建变化，整个前缀每晚泄漏一次；S3 driver 的删除走
   `trash/` + `storage_purge` 30 天回收，删库会让 trash 永不清理。
5. **不要往 `sites/demo/` 加文件。** 它是 create-jant 模板源：
   `packages/create-jant/package.json` 的 `copy-template`（`prepublishOnly` 触发）用
   `rsync -a ../../sites/demo/ template/` 整目录拷贝。
6. **demo-source 留在 Cloudflare 不动。**

## 可以复用的

### 直接复用

| 东西 | 位置 |
|---|---|
| canonical 快照 | `sites/demo-source/canonical/snapshot/` |
| Docker 镜像 | hosted 用的同一个构建（`__REPO=jant-me/jant`） |
| 部署结构 | studio `external-apps/jant/`：`.env.tpl` 契约、`compose.deploy.yaml`、`pre-deploy` profile 跑 migrate 和 assets upload、`/readyz` healthcheck、`shared` 网络 |
| 容器内 CLI | `jant migrate`、`jant site snapshot import --replace --node`、`jant uploads cleanup` |
| 清 API token | `scripts/demo-public/clear-api-tokens.mjs` —— 走 HTTP + `INTERNAL_ADMIN_TOKEN`，与运行时无关；`DEMO_PUBLIC_URL` 可覆盖目标 URL |
| 失败上报 | `.github/workflows/report-failure.yml` |
| 快照可加载性 | `src/__tests__/snapshot-canonical-replay.test.ts` 已证明快照能导进迁移到 head 的 SQLite |

### 复用逻辑，但要抽出来

`packages/core/dev/scripts/reset-node-dev.ts` 里的 `ensureLocalDevShell` 用 Node 运行时
建管理员账户、完成 onboarding、种默认导航 —— **这是唯一真正缺的生产能力**：目前没有
任何生产 CLI 命令能在 Node 上幂等地确保一个已知密码的 demo 账户。

该脚本是 dev 取向的（写 `.env.node`、dev 密码、`DEV_API_TOKEN`、只支持本地存储），
**不要复制一份改改**，把 shell 逻辑抽出来让 dev 脚本和 demo-node 共用，dev 脚本行为不变。

### 不能复用

| 东西 | 原因 |
|---|---|
| `scripts/demo-public/clear-storage.mjs` / `clear-content.mjs` / `verify.mjs` | 绑死 `queryRemoteD1` |
| `sites/demo/scripts/bootstrap-demo.mjs` 与 `ensureManagedSetup` | `flag` 直接传给 wrangler（`dev-auth-db.mjs` 的 `runWrangler([flag, ...])`），只认 `--local` / `--remote` |
| `reset-node-dev.ts` 的删库删媒体 | 本地存储专用；R2 下不能删库（约束 4） |

## 每日重建

SQLite 持久，用 `--replace`，与 Workers demo 同一模型：

| 步骤 | 说明 |
|---|---|
| 确保 demo 账户 shell | 幂等，每晚跑（对应 Workers 的 `demo-bootstrap`） |
| `jant site snapshot import --replace --node` | 清内容表、导入快照、按本站 DB 引用删掉不在快照里的对象 |
| `clear-api-tokens.mjs` | `--replace` 不清 `api_token`（不在 `SNAPSHOT_CLEAR_TABLES` 里） |
| `jant uploads cleanup` | 过期的上传会话 |
| 验证 | Node 路径，对应现有 `verify.mjs` 的检查项 |

## 背景（为什么不是为了性能）

最初以为 demo 慢是「跨太平洋 D1 往返」。实测证伪：`/readyz` 减 `/healthz` ≈ 34ms，
是同区副本，read replication 生效。真正原因是文章页约 13 次串行查询，已在另一个
会话里解决。也因此**不要试 smart placement**，它会把 Worker 从副本旁边挪走。
