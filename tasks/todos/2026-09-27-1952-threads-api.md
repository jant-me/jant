# Threads API：把 thread 做成独立资源

## 背景

- `/api/posts` 返回平铺的帖子，`/api/public/posts` 的列表返回的却是 thread 根帖，同名不同义。
  `/api/public/archive` 也是 thread 列表，名字取自页面。
- 没有接口按 thread 返回内容。公开 API 拿不到任何回复；登录版 `/api/posts` 要翻完全站再按
  `threadId` 分组。列表项里也看不出一篇帖子是不是 thread：根帖和单篇的 `replyToId`、`threadId`、
  三个时间字段都一样（一次发出的 thread 共用一个 `publishedAt`）。
- `/api/posts` 按 `lastActivityAt` 排、置顶优先：根帖按 thread 活跃度，回复按自己的发布时间，
  两层混在一起。新回复会把根帖顶过游标，遍历可能漏帖（API.md 的 Pagination 一节已写明这个风险）。
- 实测 owenyoung.com：1651 篇、17 页、93 个带回复的 thread，拼出来的与 thread 页面逐个一致，
  但同一个 thread 的回复散在不同页（`about-writing`：根帖第 1 页，回复在第 1、3、5 页）。
- 已完成的前置：`b68684a4` archive API 改按发布时间排；`91e1503f` 列表游标改为
  `lib/post-list-cursor.ts` 的不透明游标。

## 已定（2026-09-27 与 Owen 讨论）

### 命名

- 资源名说明它是什么：`posts` 是帖子，`threads` 是 thread，作者和公开两套里含义相同。
  `/public` 只表示读者视图（渲染好的正文、permalink、只含公开内容、可被 `PUBLIC_API_ENABLED` 关闭）。
- 页面名（Latest、Archive）是视图，用参数表达，不当资源名。
- Thread 用根帖 ID 标识，沿用 `threadId`。传 thread 里任意一篇的 ID 或 slug 都归一到根帖，
  响应里的 `id` 永远是根帖的。

| 含义                     | 作者（需 token）             | 公开                                 |
| ------------------------ | ---------------------------- | ------------------------------------ |
| 所有帖子，平铺           | `GET /api/posts`             | 不提供                               |
| 单篇帖子                 | `GET /api/posts/:id`         | `GET /api/public/posts/:slug`        |
| thread 列表              | `GET /api/threads`           | `GET /api/public/threads`            |
| 单个 thread              | `GET /api/threads/:id`       | `GET /api/public/threads/:slug`      |
| thread 里的帖子，分页    | `GET /api/threads/:id/posts` | `GET /api/public/threads/:slug/posts` |

- MCP：`jant_posts_list` 不变；新增 `jant_threads_list`、`jant_threads_get`、`jant_threads_list_posts`。

### `/api/public/threads`：合并公开列表和 archive

- 默认值与首页一致：排除 `latest_hidden`，按活跃度，置顶优先。等于现在的 `/api/public/posts` 列表。
- `sort` 的每个值都对应站点已有的一种排序，不另造（命名见待定 D2）：
  首页的活跃度、archive 页面默认的发布时间、archive 页面的 `?sort=updated`、collection 的
  `oldest` 和 `rating_desc`。
- 指定 `collection` 而不指定 `sort` 时，用该 collection 自己的排序和 collection 置顶，与现在一致。
- 置顶只在对应页面也置顶的排序里生效：活跃度排序用帖子置顶，collection 自己的排序用 collection
  置顶；发布时间、`updated` 不置顶（与 archive 一致）。
- `visibility` 沿用 archive 的 `public`、`featured`、`hidden`，新增 `any` 表示全部可读的内容。
- `year`、`media`、`title`、`replies`、`format`、`collection`、`lang` 从 archive 原样搬过来，
  参数名与页面一致。不认识的参数返回 400，沿用 archive 的严格校验。
- 文档写明：完整遍历用 `visibility=any&sort=published`，活跃度排序下帖子会因新回复移动。

### Thread 对象

```json
{
  "id": "pst_root",
  "postCount": 12,
  "lastActivityAt": 1790000000,
  "threadUpdatedAt": 1790000000,
  "collections": [],
  "root": { "…": "Post 对象（公开版是 PublicPost）" },
  "fold": {
    "leading": [],
    "hidden": 6,
    "gap": "pst_r3",
    "trailing": []
  }
}
```

- 列表信封是 `{ threads, nextCursor }`；`/threads/:id` 返回单个 Thread 对象，结构与列表项相同。
- `fold` 只在 `include=fold` 时返回。规则由 `lib/thread-fold.ts` 决定，回复用
  `getThreadTimelineContext` 在 SQL 里挑，不加载整串。`hidden`、`gap` 与 feed 的
  `<jant:thread>` 同名同义；没有藏掉帖子时 `hidden` 为 0、`gap` 为 `null`。
- 文档写明：挑哪几篇由站点决定，阈值可能调整；承诺的是结构、有上限、`hidden` 如实给出。
- `postCount`：已发布的帖子数，含根帖和安静回复，与 thread 页面显示的一致。

### Post 对象

- 所有帖子响应（作者、公开、MCP）加 `threadPostCount`，口径同 `postCount`，单篇为 1。
  每页一条按 `threadId` 分组的 COUNT，实时计算，不加列。
- 现有的 `lastActivityAt`、`threadUpdatedAt` 留在 Post 上，不废弃：删掉是破坏性改动，收益小。

### `/threads/:id/posts`

- 顺序与页面、feed 一致：根帖在前，回复按 `createdAt`、`id` 升序（`threadOrder()`）。
- 游标用 `lib/post-list-cursor.ts`，新增一个排序模式。回复只能接在末尾，所以边翻页边追加不会漏或重复。
- 信封 `{ posts, nextCursor }`，`limit` 默认和上限 100。
- 公开版可见性同单篇详情：private 返回 404，不含草稿，`latest_hidden` 可读。
  作者版与 `/api/posts` 一样有 `status`，默认 `published`。

### `/api/posts`

- 改为按 `coalesce(publishedAt, createdAt)` 倒序、`id` 兜底，去掉置顶优先。回复不再让旧帖移动。
  `jant_posts_list` 走同一个方法，一起变。编辑器的草稿列表用 `status=draft`（按 `updatedAt`），不受影响。

### 迁移

- 0.9：新增上面所有接口、字段和 MCP 工具，改 `/api/posts` 的排序。
  `/api/public/posts` 的列表和 `/api/public/archive` 标记废弃，行为和响应结构（平铺的
  `{ posts, nextCursor }`）都不变，内部共用 `/threads` 的查询层；响应带 `Deprecation` 头和指向
  新地址的 `Link` 头。archive 等于 `visibility=any&sort=published`。
- 1.0.1：删除这两个旧列表。`/api/public/posts/:slug` 保留。
  `/api/public/posts` 的列表路径不再用来表示别的东西。

      不沿用 `newest`：在 collection 里它指活跃度，放到 `/threads` 里会被读成发布时间。

## 实现时定下的细节

- `visibility=any` 只在 `/threads` 上有效。不用 `all`：过滤器注册表里 `all` 是「不传」的旧写法
  （`LEGACY_VISIBILITY_VALUES`），在 `/threads` 上不传表示排除 hidden，`all` 若沿用会被读成
  「全部」却排除 hidden，所以 `/threads` 对 `all` 返回 400 并指向 `any`。
- `visibility=featured`：`list()` 的 featured 过滤固定按发布时间倒序（`resolveListSort`）。
  `/threads` 不传 `sort` 时按发布时间，传了其他 `sort` 返回 400，不静默忽略。
- collection 自己的排序（`collection` 且 `sort` 为空、`activity`、`oldest`、`rating`）走
  `listCollectionThreadRootPage`，带 collection 置顶；给它加根帖过滤（子查询），这样 `year`、
  `media` 等维度也能和 collection 排序一起用。`published`、`updated` 走普通列表，collection 只是过滤。
  collection 默认排序的 rating 回退只用于默认值；显式 `sort=rating` 照办。
- 作者版 `/api/threads` 默认包含所有可见范围（含 private、hidden），与 `/api/posts` 一致；
  `visibility` 用来收窄。
- `fold.gap` 是被藏的第一篇的引用：公开版 `{ id, slug, permalink }`，作者版 `{ id, slug }`。
  展开折叠：`/threads/:id/posts?cursor=<leading 最后一篇的 id>&limit=<hidden>`，
  thread 内帖子分页和其他分页一样接受帖子 ID 作游标（只认本 thread 里调用方看得到的帖子）。
- Thread 对象不重复 `collections`：它在 `root` 上，本来就是 thread 级字段。
- `threadPostCount`：thread 里已发布的帖子数；thread 里还没有已发布的帖子时为 0。
- `/api/posts` 的新排序只用于 `published`；`status=draft` 仍按 `updatedAt`（编辑器的草稿列表依赖它）。
- 两个废弃列表保留现有路由逻辑，只加 `Deprecation`、`Link` 头和 `threadPostCount`：
  行为冻结到删除为止，重写成 `/threads` 的别名反而有改变行为的风险。它们与 `/threads` 共用
  `PostService` 的 `listPage`、`listCollectionThreadRootPage`。
