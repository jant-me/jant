# 文案风格：指南 + Skill + 可执行检查

## 背景

`docs/zh-Hans/overview.md` 里出现过这类句子：

> 帖子默认就发到首页 Latest，什么都不用选。只有想让某条安静一点、或者想把它推给订阅者时，才需要动这一项：

问题不在于"写得不好"，而在于它是模型的固定动作：预判焦虑→安抚（"什么都不用选"）、用比喻代替准确名字（"安静一点" vs `Hidden from Latest`）、虚指动词（"动这一项"）。

AGENTS.md 现有的 **UX Copy Guidelines** 只覆盖 UI 字符串（按钮、报错、空状态），不覆盖长文档散文；而且它是禁令式规则，写到第 8 个文件时早被"把事情讲清楚"的本能盖过去了。

## 关键调查结果

1. **术语真相与 AGENTS.md 相反。** `glossary.zh-Hans.yml` 没有 `Post` 条目，但它的 note 字段全部默认「帖子」（Thread→**帖子串**、Note→"Jant 的**帖子**格式之一"）。zh-Hant 同理统一在**貼文**（貼文串）。AGENTS.md 写的 `Post→文章` 是孤例，是错的。
2. **docs 里的「文章」基本是误报。** 14 处中 13 处泛指别人的文章（"我分享一些好文章"、"这篇文章说明 Jant 的设计背景"），只有 `theming.md:97` 对应英文 "Post titles"。**不能 sed。**
3. **.po 才是真正分裂的地方**：`settings/zh-Hans.po` 文章 ×20 / 帖子 ×10；`settings/zh-Hant.po` 文章 ×22 / 貼文 ×8。这些 msgid 全部含 "post"，是真分裂。
4. `public/*.po` 两个词都没出现，不受影响。
5. 顺带发现 .po 里还有别的 AGENTS.md 违规：`您`（应为「你」）、半角标点夹在中文里（`"將精選文章用於 /feed."`、`"列出貼文:"`）、翻译腔（"将 GitHub 仓库连接以自动将您的文章备份为…"）。

### 第四轮：用户指出「对偶反差」

用户点出 `overview.md:48` 的 `这是管理内容的界面，不是写东西的界面。`

模型最爱的修辞——`A，不是 B` 听起来像格言。病在于上一句已经把表单字段列全了（标题、正文、分类、标签、摘要、SEO、封面图），后半句**只提供节奏，不提供信息**，而且 B 往往是没人主张过的稻草人。

**但这条规则必须带判据，不能一刀切。** 全库扫出 13 处，**11 处是合法的**：

- `term 取自 canonical 的路径，而不是 location.pathname` —— 技术精确性
- `/en/settings 是 404，不是英文版后台` —— 纠正真实误解
- `更接近 Twitter / Threads，而不是 WordPress / Ghost 的后台` —— 点名真实参照物

判据：**「不是 B」那半句有没有给读者新信息？** 另外体裁也算数——`why-blog.md` 的 `社交媒体是分发渠道，博客是原版所在地` 是 Explanation 体裁的刻意格言，英文原文也这么写，留。

真正要改的 2 处都在 reference / how-to 体裁里：

| 位置                           | 原文                                                                    | 改后                                                             |
| ------------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `overview.md:48`               | 这是管理内容的界面，**不是写东西的界面**。                              | 那是管理内容的界面。（对比交给后面具体的 Jant 描述承担，更有力） |
| `writing-and-organizing.md:59` | …也不会被索引或缓存。**它是作者的工作地址，不是可对外分享的公开链接。** | …也不会被索引或缓存——分享给别人打不开。                          |

`.po` 里零命中。

**checker 规则只做窄的那一半。** 全量 `而不是` 会有 85% 误报，按既定原则（大部分是误报的规则会被无视）不能加。实测唯一可靠、正则能看见的信号是**对偶两边重复同一个中心词**（`…的界面，不是…的界面`）：对全库零误报，但只抓到 2 处里的 1 处（另一处是「地址/链接」，中心词不同）。取舍是**宁可只抓一半而不吵**。剩下的靠 `writing-style.md` 复查清单第 4 条人工过。

### 第五轮：用户指出「强调机器」

用户点出 `传统博客给你的是一张表单`，并给了自己的写法：
`传统博客一般会给你提供这样一个管理内容的表单：… 但是 Jant 借鉴的是更加具有人体工学的 Tumblr / Twitter 的界面`

**扫描结果修正了我的初判。** 我本来要写一条「禁 cleft 强调句」的规则，全库扫完发现 `V 的是 N` 命中 19 处，**绝大多数是正常中文**：`运行的是同一份代码`、`判断用的是字符集投票`、`前缀选中的是一个视图`、`但那里给的是回到语言页的链接`。禁它会误伤 19 句好中文。

**真正的病是三件事叠加**，单独任何一个都不是问题：

1. cleft 强调 —— 给你**的是**
2. 数量词制造揭晓感 —— **一张**表单
3. 后面跟一个单独成句的短判断当包袱 —— **那是管理内容的界面。**

用户的写法恰好把三层全拆了：判断折进名词短语（`管理内容的表单`）、加自然对冲（`一般会`）、用连接词接（`但是`）而不是并置成一个独立节拍。

**这条不加 checker 规则**：它是组合特征不是词汇特征，正则看不见。已写进 `writing-style.md` § 3 第 7 条 + 复查清单第 6 条（把「随机挑三段大声读」改成「每段都读」，并说明第 5–7 条只能靠听节拍抓）。`SKILL.md` 另加一条防过度纠正的警告，避免下次把那 19 句好中文改坏。

### 第六轮：列表被压进散文

用户问 `想到补充就 Reply 一条接成 Thread，发布只有一步。` 是不是「太排比」。

**不是排比，正相反——问题是它根本不排比。** 破折号后面挂了四个短句，四种不同语法结构：

| 片段                             | 结构                          |
| -------------------------------- | ----------------------------- |
| 打开发布界面就是正文             | 条件 + 判断                   |
| 标题可选                         | 规格表式名词 + 形容词         |
| 想到补充就 Reply 一条接成 Thread | 条件 + 三个动作串联，无连接词 |
| 发布只有一步                     | 名词 + 数量断言               |

本质是**把功能清单压进散文**，靠逗号硬串。真排比反而整齐可读，参差堆叠更难读。破折号是高发位——它承诺展开，模型就往里塞规格。

英文原文是**三项**且有 and 协调：`title is optional, you can extend any post into a Thread later, and publishing is a single action`。中文多加一项、去掉协调，还把 "a single action" 抬成「**只有**一步」。

另外两个独立缺陷：`Reply 一条` 动宾不成立，且违反术语表（`glossary.zh-Hans.yml`: Reply → 回复，`writing-and-organizing.md:69` 用的就是「回复」）。

改后：

> 但是 Jant 借鉴的是更加具有人体工学的 Tumblr / Twitter 界面：打开发布界面就是正文，标题可以不填，发布一步完成。想到补充的内容，回复一条就接成了 Thread。

同一时刻的三件事归一句、统一句式；接龙成 Thread 是另一个概念，单独成句。

全库扫「破折号/冒号后 3+ 逗号短句」只有 2 处候选，都在散文体裁且组内齐整（`一个链接、一句引用、一张随手拍的照片`），保留。此病是孤例。

写进 `writing-style.md` § 5 两条：**A list is a list**、**Counting can be an ease claim in disguise**。

**又一次没加 checker 规则**，而且这次是被数据拦下的：本想把 `一键` 加进 `zh-effort-adjective`，实测全库 6 处命中全在 `deployment.md`，对应英文 "one-click deploy"——那是 Cloudflare 该流程的**既定名称**，不是省力宣称。判据已写进指南：**数字是在命名一个东西，还是在推销它。**

### 第七轮：总纲 —— 每个字都要买到信息

用户总结出核心：**AI 写的东西废话特别多**，好写作的标准是「删无可删」。这条比前面七条删除动作更根本——**七条全是它的特例**：安抚句、意义宣称、空对偶的后半句、强调机器、压进散文的列表，无一例外都是不携带信息的字。

**但量化之后发现要加一个限定。** 把 `overview.md` 写作体验段从会话开始到现在对比：

|                  | 字数 |
| ---------------- | ---- |
| HEAD（会话开始） | 112  |
| 现在             | 134  |

**改完变长了 22 个字，而且更好。** 账：

| 删掉（零信息）                           | 换来（每处买一个新事实）                           |
| ---------------------------------------- | -------------------------------------------------- |
| `这是管理内容的界面，不是写东西的界面。` | `博客首页` —— 与「后台表单」正面咬合的承重事实     |
| `发布只需要一个步骤`                     | `更加具有人体工学的` —— 借鉴 Tumblr/Twitter 的理由 |
| `给你一张表单` 的强调机器                | `这样事后可以持续完善` —— Thread 的用途            |

所以准确表述不是「写短」，是**每个字都要买到信息**。「删无可删」只是它的一半；另一半是**该给的信息不能省**。我第六轮那个版本比两者都短却最差，因为它把承重事实和用途一起省了——那是删过头。

落地：

- `writing-style.md` 新增 **§ 0 The deletion test** 作为总纲，§ 3 七条改述为「waste 反复出现的七种形状」
- 复查清单第 1 条改成逐字删除测试，并要求反向检查「承重事实说清楚了吗」
- `SKILL.md` 开头新增 **The one rule**，并说明模型为什么会这样（训练目标是有帮助/完整，生成回路里没有任何一步会删东西，所以必须有一遍刻意的删除）
